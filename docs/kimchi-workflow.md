# Kimchi 저장소·브랜치 운영

이 문서는 `songhyun-k/crosspoint-reader-kimchi` 자체의 개발·통합 정책이다. 원본 CrossPoint에 기여할 때의 규칙과 구분한다.

## 1. 저장소와 원격의 역할

| 이름 | 역할 |
|---|---|
| `origin` | Kimchi 포크. 승인된 자체 변경과 릴리스를 게시하는 원격이다. |
| `upstream` | 원본 CrossPoint Reader. 업데이트를 읽어 오는 출처이지 Kimchi 작업의 push 대상이 아니다. |
| `ko` | 한국어 포크의 이식 참고용 원격. 필요한 변경을 출처와 함께 선택하며 기본 통합 대상으로 사용하지 않는다. |
| `freeink-sdk` | 상위 저장소가 고정한 커밋의 submodule. 일반 기능·최적화 작업 중 독자적으로 최신화하지 않는다. |

실행 전 `git remote -v`, 현재 브랜치, HEAD, 작업 트리 상태를 확인한다. 원격 이름이 달라도 실제 URL의 역할로 판단한다. `fork` 원격을 임의로 만들지 않는다. 다른 CrossPoint/KO clone의 파일은 참고만 하고 Kimchi 작업을 그곳에 적용하지 않는다.

## 2. 장기 브랜치는 `master` 하나

Kimchi `master`는 upstream 복사본이 아니라 **Kimchi 기능·최적화와 수용한 upstream 이력이 함께 쌓이는 통합 브랜치**다. 별도 장기 `develop`이나 영구 최적화 통합 브랜치는 만들지 않는다.

로컬 `master`의 tracking은 `origin/master`로 둔다. `upstream/master`를 tracking하거나 `git pull upstream`으로 자체 변경의 기준을 바꾸지 않는다. 로컬 통합 후 push 전에는 로컬 `master`가 `origin/master`보다 앞서는 것이 정상이다. 다음 작업은 이때의 로컬 `master` HEAD에서 시작하며, 오래된 `origin/master`로 되돌아가지 않는다.

작업 도구의 기본 base도 로컬 `master`로 맞춘다. 다만 다른 장치/clone에서는 아직 push하지 않은 커밋을 볼 수 없으므로, 원격 게시를 별도로 승인받아 반영하기 전에는 같은 기준이 있다고 가정하지 않는다.

## 3. 기능·최적화 작업

```text
Kimchi master → 작업 브랜치 → 검증·승인된 commit/merge → Kimchi master
                                                        └→ 다음 작업 브랜치
```

- 기능은 `feature/<주제>`, 수정은 `fix/<주제>`, 최적화는 `perf/<이슈>-<주제>`, 문서는 `docs/<주제>`로 구분한다. 작업 도구가 붙이는 사용자 접두사는 허용하며 완료된 브랜치를 이름 때문에 재작성하지 않는다.
- 각 이슈는 전용 작업 트리에서 처리한다. 작업 트리들은 같은 Git 이력·refs를 공유하지만 working directory, 빌드 결과와 미커밋 변경은 분리된다. 같은 경로에 여러 세션을 동시에 쓰지 않는다.
- 시작 기준 SHA를 기록하고 담당 변경만 커밋한다. 순차 최적화는 앞선 이슈가 통합된 `master`에서 다시 baseline을 측정한다. 독립 측정의 개선율을 단순 합산하지 않는다.
- 선형 통합은 `--ff-only`를 우선한다. 분기됐다면 차이를 확인하고 일반 merge로 통합한다. 필요한 충돌만 해결하고 해당 변경을 검증한다. 공개 이력 rebase, force push, reset으로 기준 맞추기는 하지 않는다.
- 초기 이식·완료된 작업 브랜치는 새 개발의 영구 base가 아니다. 해당 변경이 `master`에 포함됐으면 다음 작업은 `master`에서 시작한다.

## 4. upstream 업데이트 수용

```text
Kimchi master → sync/upstream-<버전 또는 SHA>
                    ├→ 선택한 upstream 커밋을 merge
                    ├→ Kimchi 변경과의 충돌 해결·검증
                    └→ Kimchi master에 이력 보존 통합
```

업데이트 작업을 명시적으로 시작할 때 upstream을 조회하고, 받아들일 버전·커밋을 고정한다. 일반 기능 작업 시작마다 upstream 최신 변경을 자동으로 섞지 않는다.

동기화 브랜치에 upstream 커밋을 **실제 merge**해 공통 조상을 보존한다. 변경 파일 복사나 upstream 전체의 squash/cherry-pick으로 대체하지 않는다. 동기화 결과를 `master`에 넣을 때도 merge 이력을 유지한다. 이미 공개한 Kimchi 패치를 upstream 위로 매번 rebase하지 않는다.

충돌 해결에서 Kimchi 언어·폰트·OTA/버전 정책과 이 문서의 브랜치 정책이 upstream 값으로 돌아가지 않는지 확인한다. submodule 갱신이 포함됐다면 고정 SHA와 영향도 함께 기록한다. 기능 추가와 동기화는 별도 작업으로 유지한다.

## 5. 검증과 승인

개발 통합과 실기기 사용 검증은 별도 상태로 기록한다. 사용자가 실기기 확인을 담당하는 작업은 관련 코드·호스트 검사와 해당 production build가 통과하면 **명시적으로 승인된 개발용 커밋·통합**을 할 수 있다. 실기기에서 확인하지 않은 응답속도·잔상·전력·안정성을 검증 완료로 표현하지 않는다.

기존 관련 테스트와 가능한 실제 코드 측정을 재사용한다. 환경 실패는 성공으로 처리하지 않고 해결하거나 미완료로 보고한다. 코드 변경 후에는 필요한 production build를 수행하지만, 문서·포맷만 바뀌거나 검증된 동일 코드가 충돌 없이 통합된 경우 같은 빌드를 반복하지 않는다. 새 테스트 프레임워크나 상시 계측 코드를 운영 절차 때문에 추가하지 않는다.

승인은 범위별이다. 구현 요청을 commit·merge·push·PR·태그·릴리스·업로드 승인으로 자동 확대하지 않는다. 승인받은 commit·merge는 수행하되 그 밖의 작업은 하지 않는다. 로컬 통합은 원격 게시나 배포가 아니다.

## 6. 작업 트리·결과·릴리스 관리

통합 전에 `git diff --check`, staged 파일 목록, `.gitignore`를 확인한다. 생성된 헤더, 펌웨어·ELF, `.pio/`, 로컬 환경 설정, 임시 측정 도구와 raw 결과를 기능 커밋에 넣지 않는다. 결과와 재현 명령은 별도 결과 디렉토리에 보관하고 다음 세션에 그 위치를 전달한다.

완료 브랜치·작업 트리는 merge 포함 여부와 미커밋/로컬 결과를 확인한 뒤 삭제 승인 범위에서만 정리한다. 기본은 보존이며 branch 삭제, worktree 삭제, prune/clean을 통합의 필수 단계로 만들지 않는다.

릴리스는 명시적으로 승인한 `master` 커밋을 기준으로 한다. 버전은 `<upstream>-kimchi.<번호>`를 사용한다. 기능 통합마다 버전을 올리거나 태그를 만들지 않으며, 태그·GitHub 릴리스·OTA 게시·기기 업로드는 별도 승인과 검증 상태 기록이 필요하다.

## 7. 다음 세션에 전달할 정보

통합 후 `git rev-parse master`로 실제 HEAD를 확인하고 다음 정보를 전달한다.

```text
대상 저장소: Kimchi clone의 실제 경로
기준 브랜치: 로컬 master
기준 SHA: 직전 작업과 운영 지침이 통합된 커밋
직전 변경: 이슈·커밋·검증 결과와 남은 사용자 확인
이번 범위: 담당 이슈 하나
작업 경로: 전용 작업 트리 또는 생성할 작업 트리
권한: 이번 세션에 허용한 commit/merge/push 범위
```

새 세션은 기준 SHA의 존재와 필요한 선행 변경 포함 여부를 확인한다. 과거 프롬프트의 조사용 커밋, 초기 이식 브랜치 또는 upstream `develop`을 새 base로 선택하지 않는다. 기존 작업 트리를 받았다면 경로·브랜치·clean 상태부터 확인한다.

## 8. upstream에 제출하는 변경은 별도

원본 CrossPoint에 PR을 보낼 때만 그 저장소의 현재 기여 규칙과 target 브랜치를 확인한다. Kimchi 고유 변경 전체를 upstream PR에 섞지 않는다. upstream의 `develop` 규칙을 Kimchi 자체 개발·통합의 기본값으로 사용하지 않는다.
